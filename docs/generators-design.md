# Generators design

Status: proposal. Nothing here is implemented.

Dyn does not have macros, templates, compile-time execution or attribute
processors, and should not gain them. Code that would need them is written by a
generator instead: an ordinary Dyn program that reads a description of the
program and writes readable files. This follows Ryan Fleury's metaprogramming:
generated code is plain code you can read, diff, step through and delete.

The compiler's only job is to describe the program. It does not find, run or
track generators. A project's build script does that.

## Rules in one paragraph

A generator is a Dyn program, by convention in `generate/<name>/main.dyn`. It
reads the program description that `dyn query` prints, and writes files
wherever it likes, starting each with a header line naming the generator. The
project's `build.sh` and `build.bat` run the generators and then `dyn build`.
Declarations can carry `@notes`, which the compiler ignores and generators
read. There is no manifest and no build program.

## Example

```dyn
// src/model/color.dyn
@names
pub enum Color { Red, Green, Blue }
```

```dyn
// generate/enum_names/main.dyn
use "std/dyn/program" program, "std/mem" mem

fn main() {
  created := mem.arena_create(mem.MiB)
  if !created.ok { #panic("arena") }
  loaded := program.load(&created.arena, "src/model")
  if !loaded.ok { #panic("program description") }
  for e in loaded.program.enums {
    if program.has_note(e.notes, "names") {
      // append "pub fn color_name(c: Color) []const u8 { case c { ... } }"
    }
  }
  program.write("src/model/color_names.dyn", text)
}
```

```sh
# build.sh
set -e
dyn run generate/enum_names
dyn build . "$@"
```

```bat
:: build.bat
dyn run generate\enum_names || exit /b 1
dyn build . %*
```

The generated `src/model/color_names.dyn` starts with
`// generated by generate/enum_names; do not edit` and is checked like any
other source file.

## Goals

- One mechanism for serializers, enum string tables, type info tables and
  data-driven code (`.mdesk`, INI, tables in text files).
- Generators are normal programs: `dyn run`, `gdb`, print statements and tests
  all work on them.
- No growth in the compiler beyond describing the program.

## Non-goals

- Running Dyn code inside the compiler.
- The compiler discovering, scheduling or caching generators.
- A manifest (`dyn.project`, `go.mod`, `Cargo.toml`) or build program
  (`build.zig`, `build.rs`).

## Why scripts and not the compiler

Running generators from `dyn build` would need process spawning, tracking of
what each generator read and wrote, stale-file cleanup, protection of
handwritten files, language server integration and new flags: likely 500 to
1000 lines of compiler code doing what three lines of shell do. A script costs
a project one `build.sh` and one `build.bat`, and generators rerun on every
build unless they check timestamps themselves. Generators are fast, so that is
the right trade.

The language server does not run generators. It sees whatever was last
generated.

## What the compiler provides

### The program description

`dyn query` already prints JSON with symbols, kinds, types, fields,
parameters, references, calls and doc comments. Generators need a little more:

| Today | Added |
| --- | --- |
| struct fields with type and position | field offset, struct size and alignment |
| enum symbols | variants with values and payload types |
| constants as symbols | constants with their folded values |
| doc comments | `@notes` with their text |

`std/dyn/program` runs `dyn query` on a module directory, parses the JSON into
an arena and offers small helpers (`has_note`, `write`). The JSON stays the
stable interface, so generators can also be written in another language.

### Notes

A note is `@name` or `@name(text)` before a declaration or a struct field:

```dyn
@serialize
pub struct Settings {
  @key("font-size") size: u32,
  theme: []const u8,
}
```

The compiler checks only the syntax and never gives a note meaning. The text
inside the parentheses is kept as written; a generator parses it if it needs
to. Notes are the one grammar addition, and the hook Metadesk tags provide,
attached to Dyn declarations instead of a separate file.

### Source positions (last)

`#from(path, line)` before a generated declaration makes diagnostics inside it
add "generated from path:line". Debug info keeps the generated file as the
line table, so stepping shows the code that actually runs. C's `#line` replaces
the line table instead, which makes generated code impossible to step through.

## Writing files

`program.write(path, bytes)`:

- writes only when the content changed, so unchanged output does not
  invalidate build caches;
- refuses to overwrite a file that exists and does not start with a generated
  header, so handwritten code is never replaced.

Removing output for renamed or deleted types is the generator's job. A
generator that writes into its own directory can clear it first.

Whether to commit generated files is the project's choice. They are readable,
so committing them is fine.

## Dependencies and `dyn.project`

`dyn.project` currently holds only `dependency NAME PATH` lines. It is replaced
by a convention: dependencies are copied into the project's `vendor/`
directory and imported by path. That is a separate change with its own
migration.

## What this replaces

| Need | Today | With generators |
| --- | --- | --- |
| Enum to string tables | handwritten `case` | generated from the enum |
| Serializers | handwritten per type | `@serialize` generator |
| Type info | always-on `#typeof` + `std/reflect` | opt-in generator writing flat `{name, kind, offset, size}` tables |
| Data-driven tables | hand-maintained Dyn tables | generated from `.mdesk` or INI data |
| Embedded files | none | `#load` (separate feature, no generator needed) |

`#typeof` and `std/reflect` stay until a type info generator has replaced their
uses in std and DNA. Removing them is a separate decision.

## Phases

1. Field offsets, struct layout, enum variants and constant values in
   `dyn query`; `std/dyn/program`. Test with an enum-names generator run from a
   script.
2. Notes in the grammar and in query output. Test with an `@serialize`
   generator against DNA's config types.
3. A type info generator in std. Measure against `#typeof`, then decide whether
   reflection stays.
4. `#from`, only if generated-code diagnostics prove hard to trace without it.

## Open questions

- Should `program.load` run `dyn query` itself, or should the script pass the
  JSON path? Running it itself keeps scripts to one line per generator.
- Is `@name(text)` enough, or do notes need structured values like Metadesk's
  `@tag(a: 1, b: 2)`? Raw text keeps the compiler out of it; a std helper can
  parse common shapes.
